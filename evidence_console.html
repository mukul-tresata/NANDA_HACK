Controlled Agent Collaboration

01 · Why multi-agents

Modularity should buy reliability.

Split a task across a retriever, a synthesizer, and a verifier — each one is easier to build, test, and trust than a single monolithic prompt doing all three at once.

Expand

This is the same bet software engineering has always made: small, single-purpose parts are predictable and debuggable in a way that one large opaque thing never is. When something fails, you know which component failed and why.

So the promise of multi-agent systems isn't “more agents” — it's that decomposition gives you back the reliability a single black-box LLM call throws away.

02 · What breaks

But the collaboration itself is ungoverned.

Nothing defines what a correct handoff looks like, checks whether an agent stayed in its lane, or predicts what the interaction will do before it has already happened. Three failure modes follow directly:

Echoing

Agents abandon their role and mirror their partner instead.

more
Even after patching, a residual rate persists — and at network scale it compounds catastrophically, not linearly. A small local rate becomes a large systemic one.
Cascade amplification

One wrong node propagates into system-wide false consensus.

more
Errors travel down the dependency graph. Hub nodes (high in-degree) are catastrophically sensitive: one bad hub poisons everything downstream of it.
Role drift

An agent's behavior quietly diverges from its assigned role mid-run.

more
With nothing structural watching, the drift is invisible — there's no mechanism to detect it, let alone correct it, before the answer ships.
03 · The gap

Structure the substrate, not just the agents.

If we inject structure and predictable determinism into how agents interact and spawn each other — not into the agents themselves — we get both worlds: the flexibility of LLM agents with the reliability of an engineered system.

Why hasn't this been done

Almost every effort so far pushes on the agents: better prompts, bigger models, more elaborate personas — making each individual smarter. The rest bolt on post-hoc checks: run the whole thing, then judge the output after the damage is done.

Neither treats the shape of the collaboration itself — who talks to whom, in what order, playing what role — as a first-class thing you can measure and govern. That's the empty lane. The hard part isn't wanting structure; it's finding a representation of “a good collaboration” that a machine can actually compute and act on. That representation is what the rest of this is.

Reference The idea ◆ONE COORDINATE SYSTEM

A task's required shape, and the plan's distance from it

One shared coordinate system underlies every claim that follows. The gap it exposes is what makes the rest possible.

Two objects, one coordinate system

The task fingerprint → F

Every task has a required shape, fixed before a plan is built.

So we stop treating the task as one opaque embedding. We read it, deterministically, as an orthogonal signature — a few independent structural dimensions, each an answer, not a number:

information flowsequential
epistemic stancesynthesis
output contractartifact
decomposabilitycoupled
complexitymedium
volatilitystable

That signature is F — the required flow, depth, and roles the plan must have. No LLM in the read.

The fingerprint gap → E

How far the built plan sits from that shape.

Build the plan, run it, then score its distance from F on four geometric axes — partition · flow · role · scale, each in [0,1]. Same space, so phrasing washes out: one axis, one defect, one fix that transfers to every task of the shape.

Why this is the whole game: “a good collaboration” stops being a vibe and becomes a measurable coordinate. Measure it, and you can improve it, guarantee it, and reuse it.

Content quality & the verdict

A second, content-quality tensor rides alongside the structural four — groundedness · relevance (generation-side RAGAS, computed mechanically, no LLM judge). The final verdict is one uniform gate over all six axes: every axis under threshold → good; one axis barely over → mixed; otherwise → poor.

No weighted sum collapsing the axes into a single number — that's a deliberate stance. A weighted sum lets a good axis mask a bad one; keeping the vector intact means the system always knows which thing is wrong, which is exactly what makes targeted repair possible.

Reference Mechanism ◆ONE RUN, END TO END

The same coordinate system, in motion

How a single run moves from task to answer — and the modules that implement it.

How information flows through one run

A task enters as raw text and leaves as a composed answer. In between, two loops give the system its guarantees: an inner repair loop that descends on error, and an outer memory loop that carries what worked forward to the next task of the same shape.

data flow inner repair loop (DESCEND) outer memory loop (REUSE)
Step-by-step

1–2 · Classify. RESEARCH.clarify() turns raw intent into the structural fingerprint; compute_required() derives F. Both deterministic.

3–6 · Plan & run (inner loop). The conductor builds a DAG — warm-started from the store if this shape has been seen before. The KERNEL executes it; DELTA measures E, names the worst axis, and either applies a deterministic graph repair or asks the conductor to replan. The delivered plan updates only under PRESERVE — it can hold still or improve, never regress.

7–8 · Deliver. compose() writes one coherent answer; Q-factor (groundedness, relevance) folds into the final verdict.

Outer loop · learn. The best plan for this structural species persists to the F-keyed store, so the next task of the same shape starts warm instead of cold.

Reference Methodology ◆ABOUT EVIDENCE.PY

Where these numbers come from

Every claim above is read from a JSON file this script writes — nothing on this page is invented or hand-tuned for the demo.

Running the battery

scripts/evidence.py prints a live, human-readable trace of all 5 claims, then writes scripts/evidence_results.json — the machine-readable payload this page renders. Re-run it any time to refresh the data; drop the resulting file onto this page to load it.

# full evidence battery — (re)writes scripts/evidence_results.json python3 -u scripts/evidence.py # one task, programmatically python3 -c "from ceo_delta import Orchestrator, Config; \ r = Orchestrator(Config(), workdir='.demo').run('Explain how a C compiler works'); \ print(r.report.verdict, r.report.ef_tensor)"

The richest live object is RunResult (returned by Orchestrator.run()): answer, report.verdict, report.ef_tensor, report.q_tensor, report.required_structure, iterations, ef_trace, ef_incumbent_trace (the monotone curve), ef_move_log, dag.nodes.
